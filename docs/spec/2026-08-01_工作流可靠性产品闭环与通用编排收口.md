## 1. 文档定位

本 SPEC 是当前工作流实现的整改与收口合同，解决以下九类问题：

1. 判定节点可能表现为重复执行，失败后任务不能正常结束。
2. 已正常结束的 Run 缺少“再来一轮并修改提示词”的人工入口。
3. 每次运行无法配置业务循环轮次。
4. 自由定义工作流尚未形成可运行闭环。
5. 提示词配置缺少清晰、可用的上一轮结果入口。
6. 首次进入与再次进入的提示词边界和必配规则不明确。
7. Project 工作流历史缺少稳定入口和血缘展示。
8. 从资源管理器点击文件时，中间区域不再显示预览。
9. 从工作流页面返回恢复会话时，终端样式和渲染状态可能异常。

本 SPEC 已合并项目级入口、Run 生命周期、可靠性、历史、V1 兼容和 V2 通用编排的最终口径，是当前工作流交付唯一保留的产品合同。此前阶段性设计文档只在 Git 历史中保留，不再作为开发规则或事实来源。

各主题在本文中的权威位置如下：

## 2. 已确认的现状与根因

### 2.1 判定重复与 Run 不结束

最近一次异常 Run `workflow_run_060dd98ca3f9ebf271` 显示：

- `code-decide` 第 1 次 attempt 因 `workflow_decision_invalid` 失败。
- 模板允许 `maxAttempts=2`，引擎随后创建第 2 次 attempt。
- 第 1 次 attempt 对应的 Orchestration Task 和 Worker Dispatch 没有先进入终态，仍分别停留在 `dispatched` 和 `ready`。
- 旧任务未收口时新任务已经派发，因此用户看到类似同一判定执行两次；旧任务也会阻断 Run 的正常结束与恢复。

当前实现还有两项放大因素：

- 结果解析失败发生在正常完成回执之前，失败路径没有完成与成功路径对等的任务、派发和事件收口。
- 判定协议同时存在两种口径：部分编辑器提示要求首行为“完成/不完成”，V1 运行时解析器仍要求 `approve/revise/request-human/stop-at-review`。同一逻辑层出现两套协议会制造非业务失败和自动重试。

结论：问题本质不是简单的按钮双击，而是 attempt、任务派发和 Agent 完成回执没有共享一个可恢复、幂等的终态协议。

### 2.2 已完成 Run 缺少人工续跑

当前终态 Run 主要提供详情查看；Activity 中的“Configure another run”更接近清空当前选择并重新配置，不能表达：

- 以哪个已完成 Run 为基础；
- 保留哪一版模板与历史；
- 人工补充了什么新要求；
- 新旧 Run 之间是什么关系。

直接重新打开终态 Run 会破坏不可变审计，也会让步骤、attempt、事件和最终结果失去稳定语义。

### 2.3 运行级轮次配置缺失

当前轮次或复核次数主要来自模板配置，Run 启动页只展示结果，不能为本次运行覆盖。实现中还混用了两个概念：

- attempt：同一步因技术性失败而重试；
- cycle/route traversal：业务结果“不完成/需修订”后沿回路再次执行。

二者必须分开计数、展示和审计。

### 2.4 自由定义工作流尚未可运行

当前 V1 运行模型仍围绕 produce/review/decide/human-gate/complete 等固定业务角色，输入也包含 artifact、review aggregate 等专用绑定。编辑器虽然能创建空白工作流，但默认 Produce → Complete 与 V1 启动校验要求的 Produce → Review 不一致，空白模板并非真实可运行的自由编排。

因此不能继续通过增加 V1 特例来模拟通用工作流。通用能力必须按 V2 的 agent/decision/human/end、通用输出、条件路由和相对历史变量完成。

### 2.5 历史占位词不是完全缺失，而是缺少产品化入口

运行时和历史引用选择器已有相对轮次能力，但：

- 常用占位词列表没有明确的“上一轮本节点结果/上一轮上游节点结果”。
- 部分内置模板的首次与再次进入提示词相同，默认不会带入历史。
- UI 没有阻止首次提示错误引用负轮次，也没有要求可达回路的再次提示显式读取历史或声明不读取。

问题是语义入口、默认配置和校验不完整，不应再增加含义模糊的全局 `previousConclusion` 字符串。

### 2.6 历史能力已有实现，但信息架构不可发现

当前已有 Workflow Run History 和搜索、筛选、详情能力，但入口依赖当前 Run 或页面状态，不能稳定表达“查看当前 Project 的历史”。Renderer 的模块内状态在重载后也可能丢失当前页与筛选。

本期范围是 Project/Workspace 的工作流运行历史，不扩张为 Git 分支、工作树、文件变更和所有工程事件的统一审计系统。

### 2.7 文件预览回归来自工作区表面未切换

资源管理器点击文件时仍调用 `openFile(..., { preview: true, focusEditor: true })`，但没有统一将中间区域从 workflow surface 切回 workspace surface。文件标签可能已创建，EditorPanel 却仍因 Workflows 为 active view 而隐藏。

这不是资源管理器单点问题。任何激活编辑器、浏览器或终端内容的入口，都应执行统一的工作区表面激活事务。

### 2.8 恢复会话样式回归来自终端可见性语义错误

进入工作流页面时，工作树仍在，但 workspace panes 被隐藏；终端层把这种普通 Tab 遮挡当成整个工作区 surface 被挂起，执行重型 `suspendRendering`。返回时再走 resume/fit/WebGL atlas 恢复路径，可能破坏字体度量、行列数、颜色或已同步 TUI 的显示。

工作流 Tab 的遮挡应与普通内容 Tab 切换使用同一套轻量隐藏/显示语义，不能触发只有窗口、工作树或真正 surface 挂起时才需要的重型终端恢复。

## 3. 目标与非目标

### 3.1 目标

- 每个步骤 attempt 都能可靠进入唯一终态，恢复或重复回调不会制造第二个有效派发。
- 技术重试与业务循环有独立数据、预算、UI 和事件。
- 已完成 Run 可以通过中间区域创建有血缘的新 Run，并为新 Run 修改一次性提示词和轮次预算。
- Project 工作流历史始终可进入，可查看 Run 血缘、配置快照和终态结果。
- 提示词编辑器明确区分首次进入与再次进入，并提供稳定的相对历史变量。
- V2 自由定义工作流具备从编辑、预检、执行、人工介入到历史回放的最小闭环。
- 文件预览与会话恢复两个回归修复，并纳入长期自动化。

### 3.2 非目标

- 不在本期构建覆盖 Git、工作树、终端命令和文件版本的完整“工程历史”。
- 不允许用户从已完成 Run 原地续写或修改历史记录。
- 不将 Agent 身份、生命周期、完成回执职责下放给工作流业务提示词。
- 不通过新增 SPEC/Artifact/Review 等专用节点实现自由编排。
- 不在 P0 阶段重做整套工作流视觉设计。
- 不在本 SPEC 内承担跨平台、SSH 远程执行、截图录屏或真实人工验收。

## 4. 冻结决策

### D1. 终态 Run 不可变

“再来一轮”必须创建新的 child Run。旧 Run 的步骤、attempt、事件、提示词快照和最终结果均不可修改。

### D2. 默认继承原模板快照

从 `completed` Run 发起“再来一轮”时，第一版只允许继承原 Run 的模板版本快照。若用户希望使用模板最新版，应退出该流程并创建普通新 Run，避免一次操作同时改变历史上下文与流程结构。

### D3. 历史沿 Run 血缘只读解析

child Run 不复制父 Run 的步骤记录。历史解析器沿 `parentRunId/rootRunId` 读取只读前缀；child Run 自己继续追加事件。

血缘编号使用以下冻结语义：

- `lineageCycle`：在 root Run 血缘中单调递增，作为 `history[round]` 与相对轮次的索引。
- `localRunCycle`：仅用于 UI 展示和本次 Run 预算统计，从 1 开始，不进入提示词历史寻址。
- `visit`：同一稳定 node ID 在整条血缘中的进入次数；child Run 会接续 parent 的 visit。
- `attempt`：当前 visit 内的技术重试次数，每个新 visit 从 1 开始。
- 只有成功完成并已持久化的节点输出进入 history 索引；失败、取消、仅投递或仍在运行的 attempt 不进入索引。

V1 兼容映射固定如下：

- 既有 `workflow_step_runs.round` 保持表示 `localRunCycle`，避免改变旧 Run、review budget 和现有详情语义。
- child Run 的步骤新增或派生 `lineageCycle`；普通 root Run 中 `lineageCycle = round`。
- 提示词中的 `history[n]`、`history[currentRound]` 和负相对轮次均以 `lineageCycle` 为坐标；直接变量 `{{round}}`、`{{currentRound}}` 以及 V2 的 `{{cycle}}` 也表示当前 `lineageCycle`。
- Run 详情同时显示“本次 Run 第 N 轮”和“血缘第 M 轮”，避免把两套数字都简称为 round。

对 child Run 首个步骤而言，如果血缘中已有该节点成功结果，则使用“再次进入”提示词。负相对轮次以当前即将执行步骤的 `lineageCycle` 计算，`history[-1]` 解析上一血缘轮次，不因切换 Run 而重置。

最小数值例子：

```text
parent lineage cycle 1：produce=P1 → review=R1 → judge=不完成
parent lineage cycle 2：produce=P2 → review=R2 → judge=完成

child 从模板入口启动：
lineageCycle = 3
localRunCycle = 1
produce visit = 3
produce attempt = 1
匹配 repeatVisit
history[-1] 解析 lineage cycle 2 的 P2/R2/judge 输出

若 child 第 3 血缘轮仍不完成并沿回路返回：
下一次 produce 的 lineageCycle = 4、localRunCycle = 2、visit = 4、attempt = 1
history[-1] 解析 child 自己第 3 血缘轮的结果
```

### D4. 技术重试不等于业务轮次

- attempt 只处理超时、协议错误、Agent 异常等技术失败。
- cycle/route traversal 只处理工作流条件分支形成的业务回路。
- 两类计数不得共享字段，也不得在 UI 中统一称为“重试”。

### D5. V1 判定协议在迁移前保持唯一

P0 的 canonical protocol version 固定为 `v1-approve-revise`，并由共享定义同时生成编辑器提示、运行时解析、预检和测试：

| canonical token  | Review 可用 | Decision 可用 | 旧模板兼容别名                               |
| ---------------- | ----------- | ------------- | -------------------------------------------- |
| `approve`        | 是          | 是            | `通过`、`批准`                               |
| `revise`         | 是          | 是            | `需要修改`、`需要修订`、`不通过`、`退回修改` |
| `request-human`  | 是          | 是            | `请求人工`、`人工处理`、`人工确认`           |
| `stop-at-review` | 否          | 是            | `停在评审`、`止于评审`                       |

- 新建或编辑后的 V1 提示词只能生成 canonical 英文 token；中文别名只用于未标版本或既有 V1 模板的兼容读取。
- V1 中“完成/不完成”是非法判定，不作为上述别名。
- 非法输出先形成结构化失败并完整收口原 attempt/task/dispatch，再根据 retry policy 决定是否创建下一 attempt。
- V2 的 protocol version 固定为 `v2-binary-zh`，届时模板协议、提示生成和解析器同批切换为“完成/不完成”，不与 V1 在同一模板中隐式混用。

### D6. V1 保持兼容可编辑

P0/P1 可以修复 V1 执行和兼容已有模板，但不再增加新的 V1 专用节点或输入类型。V1 与 V2 模板均可继续运行和查看历史；模板不存在活动 Run 时允许直接编辑并保存不可变新版本，存在 `running/paused/waiting-human/review-limit-reached` Run 时锁定编辑。既有 Run 始终读取启动时的模板快照，不被后续模板版本修改。

### D7. 中间区域只有一个 active surface

Workflows、Editor、Browser、Terminal 可以保留各自标签和状态，但任一时刻只有一个中间区域 surface 激活。打开或激活 workspace 内容必须原子地切回 workspace surface。

## 5. P0：执行可靠性与界面回归

P0 是发布阻断项，必须先于“再来一轮”和通用工作流交付。

### 5.1 attempt 终态 reconciliation

当前 Workflow Store 与 Orchestration Store 虽然打开同一个 `orchestration.db` 文件，但分别持有独立 SQLite connection，不能把跨 Store 写入描述为现成的物理单事务。P0 采用持久化 reconciliation record 实现可恢复的逻辑原子性，不要求在 P0 重构两套 Store 共用连接。

每个 Agent 最终响应按以下顺序处理：

```text
completion receipt 持久化
→ 响应协议校验
→ Orchestration task/dispatch 幂等收口
→ Workflow attempt/step/event 与可选 retry outbox 幂等收口
→ reconciliation settled
→ retry outbox consumer 以 CAS 创建下一 attempt（如需要）
```

最小 reconciliation record 应包含等价信息：

```ts
type WorkflowCompletionReconciliation = {
  receiptId: string
  runId: string
  stepRunId: string
  attempt: number
  taskId: string
  dispatchId: string
  messageDigest: string
  outcome: 'succeeded' | 'failed'
  state: 'received' | 'orchestration-settled' | 'workflow-settled' | 'settled'
  retryOutboxState: 'none' | 'pending' | 'consumed'
}
```

约束：

1. receipt 先持久化；相同 identity 与 digest 的重复回调返回同一 reconciliation，不重复处理。
2. 协议校验产生成功结果或结构化失败，原始响应保留在受控诊断存储中。
3. Orchestration Store 以 task/dispatch 当前状态执行幂等终态转换；已处于相同终态视为成功，不允许覆盖冲突终态。
4. Orchestration 收口成功后，Workflow Store 在自己的单事务中写入 attempt/step 终态、结果或失败信息、事件、reconciliation 状态，以及需要重试时的 pending outbox；此时不得直接创建后继 attempt。
5. 只有 reconciliation 达到 `settled`，并确认旧 task/dispatch 已终态，outbox consumer 才能以 CAS 创建一个后继 attempt，再将 outbox 标记为 consumed。
6. 任一步骤崩溃后，恢复协调器从最后持久化 state 继续；不得重新解释为一次新 completion。

协议解析失败也必须走完整 reconciliation。不能因为没有生成有效业务报告，就跳过任务与派发收口。

### 5.2 唯一活跃派发约束

P0 的 V1 逻辑执行键冻结为：

```text
logicalExecutionKey = runId + nodeId + round + assignmentKey
```

- `round` 是 V1 的业务评审轮次。
- `assignmentKey` 使用当前持久化的稳定分配键，区分同一 review node 的并行 Reviewer。
- 每个技术重试创建新的 stepRunId，并在同一 logicalExecutionKey 下递增 attempt。
- stepRunId 标识一次 attempt，不作为 attempt lineage 的稳定键。
- V2 改用 `runId + nodeId + visit + assignmentKey`，不反向改变 V1 历史键。

同一 logicalExecutionKey 最多存在一个非终态 Worker Dispatch。持久化 ownership record 保存当前 `stepRunId/attempt/taskId/dispatchId/state`；切换 ownership 前必须通过 CAS 验证旧 owner 已终态。实现必须同时具备：

- 数据库唯一性或等效持久化约束；
- ownership CAS 和状态检查；
- 重启恢复后的幂等重放；
- 并发完成回调和超时回调的竞争测试。

仅依赖 Renderer 禁用按钮、内存锁或事件顺序不满足要求。

### 5.3 失败后的 Agent/任务收口

- Engine 负责 Agent identity、任务 lifecycle、transcript/result 收集与 `worker_done` 协调。
- 工作流业务 Agent 只负责当前业务步骤，不负责猜测是否应终止任务。
- 任一 attempt 失败后，原任务必须明确进入 `failed/cancelled` 等终态，再派发下一 attempt。
- 如果无法确认旧派发所有权或终态，Run 使用既有一等状态 `waiting-human`，waiting reason 取 `delivery-uncertain` 或 `lifecycle-mismatch`，不得新增只存在于日志文本中的 `blocked/recovery-required`。
- 处于上述 waiting reason 时，恢复协调器禁止自动重派；UI 根据有效 Resolution Offer 提供查看证据、确认重复风险后重试、重新分配或结束工作流。
- 达到 maxAttempts 后，步骤和 Run 必须根据模板策略进入失败或人工等待，不得停留在 running/dispatched。

### 5.4 判定协议统一

- 建立单一的 V1 decision protocol 定义，提示词生成、编辑器预览、运行时解析和测试共同引用。
- 保存模板时写入 `decisionProtocolVersion = 'v1-approve-revise'`。
- 输出协议说明属于 Engine 固定约束，编辑器只允许修改业务提示词；预览必须同时显示最终追加的协议说明。
- 未标版本的既有模板按 V1 兼容读取；V1 业务提示中出现“第一行只能是完成/不完成”等已知冲突约束时，预检阶段阻断，而不是运行后自动重试。
- 原始 Agent 文本必须保存在 attempt 诊断信息中，不能只保留解析错误。

### 5.5 文件预览 surface 激活

建立共享的 workspace content activation action，至少包含：

- 激活目标编辑器组；
- 设置 workspace surface 为 active；
- 打开或激活目标文件 Tab；
- 根据调用参数决定 preview/pinned 和键盘焦点；
- 保留 Workflows Tab，但将其设为非激活。

资源管理器、快速打开、搜索结果、问题面板和其他文件跳转入口统一调用该 action。不得只在 Explorer click handler 里补一个局部 `setActiveView`。

### 5.6 会话恢复与终端渲染

- Workflows 与普通内容 Tab 的切换使用轻量 `hidden/reveal` 语义。
- 只有窗口隐藏、工作树真正离场、宿主 surface 被销毁等场景才允许 `suspendRendering`。
- 普通 Tab 返回使用已有的轻量 present/reveal 路径，保留共享 WebGL glyph atlas。
- 不重新创建终端模型，不丢弃已同步 buffer，不无条件重算字体或清屏。
- 恢复时若确需 fit，必须在容器获得稳定尺寸后执行，并避免把 0 宽高写入 rows/cols。

### 5.7 P0 验收门槛

| ID    | 场景                                     | 通过条件                                                     |
| ----- | ---------------------------------------- | ------------------------------------------------------------ |
| P0-R1 | 判定输出非法，允许 2 次 attempt          | 第 1 个 task/dispatch 先终态，第 2 个才创建；最终 Run 可结束 |
| P0-R2 | 同一完成响应重复投递                     | 只生成一次结果、一次终态事件和至多一个后继 attempt           |
| P0-R3 | reconciliation 任一阶段重启应用          | 恢复后从持久化 state 续作，无重复派发，Run 收敛到可解释状态  |
| P0-R4 | 超时与完成回调并发                       | 只有一个终态胜出，另一路幂等返回                             |
| P0-R5 | Workflows 激活时点击资源管理器文件       | 文件立即在中间区域预览，Workflows Tab 保留但不激活           |
| P0-R6 | 连续点击两个预览文件                     | 遵守现有 preview replacement 规则，不堆积错误 Tab            |
| P0-R7 | 恢复的 Agent 会话 → Workflows → 返回终端 | 字体、颜色、行列数、TUI 内容和分屏布局不变                   |
| P0-R8 | 本机 Folder workspace、本机 Git worktree | 文件预览和终端恢复均满足同一语义                             |

P0 合入门槛：

- P0-R1 至 P0-R4 必须有自动化测试。
- P0-R5 至 P0-R8 必须包含自动化交互测试。
- 实现和测试代码仍必须保持跨平台、Folder workspace 与 SSH 兼容，不得为通过本机验收硬编码 macOS 或本地路径。

跨环境边界：Windows、Linux、SSH 实机和跨平台安装包矩阵已从本 SPEC 移出。当前 SSH Workflow 以安全拒绝作为明确能力边界；未来启用远程 Workflow 时必须另立恢复与 Host 隔离需求。

## 6. P1：已完成 Run 的人工续跑

### 6.1 入口与交互

第一版只在 `completed` Run 详情页提供“再来一轮”主操作。`failed/cancelled/review-limit-reached` 等状态继续使用各自的恢复、重新配置或人工决策入口，不与正常完成后的再次运行混为同一动作。

点击“再来一轮”后进入 child Run 配置态，页面同时展示：

- 来源 Run、完成时间、模板快照版本和最终结论；
- 最近一轮关键节点结果，只读；
- 本次人工补充要求；用户必须填写内容，或者显式勾选“无额外要求”；
- 可编辑的一次性步骤提示词覆盖；
- 本次运行的业务轮次预算；
- Agent 分配与预检结果。

页面说明固定使用“从流程入口重新执行，并读取来源 Run 的只读历史”，不能使用“从断点继续”“恢复原任务”等文案。入口节点在 parent 血缘中已有成功输出时会匹配 `repeatVisit`，这属于带历史前缀的全图重跑，不是 checkpoint resume。

第一版 child Run 始终从模板入口重新执行，不支持选择任意节点续跑。任意节点续跑必须等 V2 图执行器具备完整的输入可达性和历史校验后另立需求。

### 6.2 Run 血缘

Run 持久化至少增加等价字段：

```ts
type WorkflowRunLineage = {
  parentRunId: string | null
  rootRunId: string
  rerunReason: string | null
  noAdditionalRequirements: boolean
}
```

约束：

- 普通新 Run：`parentRunId = null`，`rootRunId = self`。
- 再来一轮：`parentRunId = sourceRunId`，`rootRunId = source.rootRunId`。
- 第一版 parent 必须是 `completed` Run，且属于同一 Project/Workspace 权限边界。
- `rerunReason` 非空与 `noAdditionalRequirements=true` 必须二选一，不能同时为空或同时生效。
- 禁止血缘环。
- P1 不支持单独硬删除血缘中的某个 Run；归档只影响默认可见性，不删除步骤、事件或输出，历史解析仍可读取归档 parent。
- 若未来增加隐私硬删除，必须以整条 root lineage 为一致性边界，或先物化 child 所需历史快照；不得留下无法解析的半条血缘。

### 6.3 一次性提示词覆盖

提示词覆盖属于 child Run 配置，不修改模板。建议使用等价结构：

```ts
type WorkflowRunPromptOverrides = Record<
  string,
  {
    firstVisit?: string
    repeatVisit?: string
  }
>
```

- key 为稳定 step/node ID。
- child Run 因继承父级历史而匹配 repeatVisit 时，UI 默认打开对应覆盖项。
- Engine 固定追加的身份、输出协议和安全约束不可被覆盖。
- 启动后覆盖内容冻结并写入 Run snapshot；历史详情展示实际生效提示词及来源“模板/运行覆盖”。
- 创建 child Run 的 mutation 必须有 request ID 和幂等结果，防止双击生成两个 Run。

### 6.4 Agent 分配

可以预填父 Run 的 Agent 选择，但必须重新进行 availability、workspace/host、ownership 和 idle 状态预检。不得因为是 child Run 就跳过预检或复用旧 Provider Session 作为新任务身份。

## 7. P1：每次运行可配置业务轮次

### 7.1 规范语义

P1 先为当前 V1 提供可真实执行的运行级预算，不以 V2 字段假装完成 V1 能力。V1 policy version 固定为 `v1-review-rounds`：

```ts
type WorkflowRunPolicyOverridesV1 = {
  policyVersion: 'v1-review-rounds'
  maxReviewRoundsByNodeId: Record<string, number>
}
```

- key 为 V1 稳定 review node ID。
- Run 初始有效轮次 = Run override ?? template `reviewPolicy.maxReviewRounds`。
- 运行中的人工扩展单独记录，不能覆写或伪装成初始 override。
- 最终有效上限 = 初始有效轮次 + 有审计记录的人工扩展。
- 单 review 回路模板显示一个“最多评审轮次”；存在多个 review node 时，在高级区域逐节点配置。
- P1 不向 V1 暴露 route traversal，也不把 review node 预算描述成通用路由预算。
- attempt 的 maxAttempts 继续由模板/系统可靠性策略控制，本期不开放给普通运行配置。

V2 policy version 固定为 `v2-route-traversals`，并按通用工作流 SPEC 使用：

```ts
type WorkflowRunPolicyOverridesV2 = {
  policyVersion: 'v2-route-traversals'
  maxTraversalsByRouteId: Record<string, number>
}
```

V2 UI 对常见单回路可以显示“最多执行轮次”，但必须按以下固定规则换算：

```text
maxTraversals = 2
→ 允许沿该回路跳转 2 次
→ UI 显示“最多 3 轮”（首轮 + 2 次返回）
→ 第 3 轮结束后若仍不完成，进入配置的 human/end，不再派发
```

V1 与 V2 policy snapshot 按 `policyVersion` 分支读取，不共享含义不同的无版本字段。

### 7.2 配置与冻结

- 普通新 Run 和“再来一轮”都必须显示本次有效轮次。
- 合法范围由系统常量统一定义；Renderer 与主进程都校验。
- Run 启动后配置冻结。
- 运行中确需增加预算时，只能通过人工等待页的“增加轮次预算”动作完成，写入独立的审计事件，不能静默修改原 snapshot。
- 超过预算时，Run 按模板定义进入 human 或 end，不得继续派发。
- child Run 的预算只统计本次 Run 的 `localRunCycle` 或本 Run 内 route traversal；parent 已使用轮次仅作为历史，不消耗 child 的新预算。

### 7.3 显示与审计

Run 详情和历史页同时展示：模板默认值、Run 覆盖值、运行中人工扩展值和实际已使用次数。业务轮次与技术 attempt 使用不同标签和事件类型。

## 8. P1：提示词历史变量与边界

### 8.1 常用历史变量

在提示词插入器中增加语义化选项：

- 上一轮本节点结果；
- 上一轮上游节点结果；
- 上一轮指定节点结果；
- 指定历史轮次的指定节点结果。

这些只是 UI preset，落盘必须展开为通用、稳定的历史引用，并保存明确 node ID。不得落盘为含义依赖当前 UI 选择的 `previousConclusion`。

### 8.2 首次进入与再次进入

提示词配置使用两个固定、可同时看到状态的区域：

1. **首次进入**：必配；禁止引用负相对轮次。
2. **再次进入**：存在可达回路时必配；必须至少引用一个历史结果，或者显式勾选“本提示词不读取历史”。

页面必须使用持续可见的标题、必填标记、说明和行内错误。关键边界不得只依赖 Tab 颜色、tooltip 或 toast。

### 8.3 校验与预览

模板保存和 Run 预检都执行：

- 首次/再次条件是否覆盖所有可达 visit；
- 负相对轮次是否可能越界；
- 被引用的 node 是否稳定存在且在路径上可达；
- 再次提示是否读取历史或显式声明不读取；
- 完成条件是否已配置且被判定提示引用；
- 使用当前 Run/血缘上下文生成首次和下一次进入的实际提示预览。

缺失历史引用必须在预检阶段阻断并给出具体 node/round，不得默认为空字符串继续运行。

## 9. P1：Project 工作流历史

### 9.1 已有能力与本期缺口

P1 在现有 Workflow Run History 上补齐产品闭环，不重写已经存在的查询与详情：

| 能力                   | 当前状态                      | P1 工作                                     |
| ---------------------- | ----------------------------- | ------------------------------------------- |
| Run 列表               | 已有                          | 保留并增加血缘分组                          |
| Workspace/Project 范围 | 已有切换，当前默认 Workspace  | 默认改为当前 Project，保留 Workspace 切换   |
| 状态、模板、日期筛选   | 已有                          | 保留并持久化非敏感筛选                      |
| 文本搜索               | 已有 Renderer 过滤            | 保留；数据量超过本地上限时再改为存储层搜索  |
| Run 详情、步骤、事件   | 已有                          | 增加 lineage、预算、提示词来源和阻断摘要    |
| Markdown/JSON 导出     | 已有                          | 导出补齐 lineage、policy 与 prompt override |

| 页面与筛选恢复         | 模块内状态，重载丢失          | 持久化最近页面和非敏感筛选                  |

### 9.2 稳定入口

Workflows 中间区域提供稳定的一级或二级导航：

- 模板；
- 运行配置/当前运行；
- 历史。

无论当前是否存在 active Run，“历史”都必须可进入。默认筛选当前 Project，允许切换到当前 Workspace；页面重开时恢复最近的页面与非敏感筛选。

Workflows 仍是临时内容 Tab，不要求在应用重启后自动重新打开；但一旦打开，历史数据必须从持久化存储完整加载。

### 9.3 历史列表与详情

沿用现有状态、模板、日期和搜索能力，并补充：

- parent/root Run 标识；
- 普通运行/再来一轮标签；
- 第几次血缘运行；
- 模板快照、轮次预算和提示词覆盖摘要；
- 最终结果、失败原因和阻断原因；
- 从任一 `completed` 详情发起“再来一轮”。

血缘默认按 root Run 分组，可展开查看每个 child。列表和详情不得通过读取当前内存 activeRun 拼装历史。

### 9.4 范围边界

页面命名应明确为“工作流历史”或“运行历史”。如果后续需要完整 Project 工程历史，应单独设计 Git、文件、终端和工作流事件的统一时间线，不在本期借用现有页面名制造错误预期。

## 10. P2：自由定义工作流 V2

P2 的通用节点、历史变量、路由模型、交付顺序和兼容门槛均以本节为准。

状态：已完成。当前交付已具备通用编辑、预检、执行、历史、恢复、重试、并发收口、人工节点和三个代表模板的自动化闭环；后续真实使用中的交互和业务调优按新需求处理。

### 10.1 最小可运行闭环

V2 首个可发布版本必须同时具备：

- `agent / decision / human / end` 四类通用步骤；
- 稳定 node ID、通用 node output 和 append-only history；
- 模板化输入、相对历史引用和预检；
- “完成/不完成”二元判定及条件路由；
- 每条回路的 traversal budget；
- 人工等待、继续、结束和预算扩展；
- transcript/result 收集与统一 `worker_done` 生命周期；
- Run 历史、恢复、child Run 血缘和导出。

任何只完成画布、不具备真实执行器与历史恢复的版本，不得标记为“自由定义工作流已完成”。

### 10.2 空白模板处理

- 在 V2 执行器能运行空白模板生成的默认图之前，隐藏或禁用“新建空白工作流”，并解释当前仅可复制可运行模板。
- 不得为让 Produce → Complete 通过而放宽 V1 校验并引入新的不一致。
- V2 启用后，空白模板初始图必须是可通过预检并能真实结束的最小图。

### 10.3 V1 迁移

- 先实现 V2 history/dispatch/result 的底层通用能力，再接 V2 编辑器。
- 提供 V1 snapshot 兼容适配器，历史 Run 永远按原协议可读。
- 既有 V1 模板继续可运行；按 D6 在无活动 Run 时仍可编辑。空白新建入口默认创建 V2。
- 内置模板逐个迁移并做快照对比，不原地覆写用户模板。
- 本期不移除 V1 编辑能力。

### 10.4 三个代表性验收模板

至少用以下不同结构证明 V2 不是特例实现：

1. 单 Agent → End，无回路。
2. Agent → Decision → 不完成回 Agent / 完成到 End。
3. 多 Agent 串并行输入 → Decision → Human → 继续或结束。

三个模板必须只使用通用节点、通用输出、历史变量、条件和人工决策，不允许业务专用 runtime 分支。

## 11. 数据与事件合同

### 11.1 必需的持久化信息

实现可以调整表名，但必须可稳定查询以下信息：

- Run：template snapshot/version、workspace/project/host、lineage、lineageCycle offset、带版本 policy overrides、prompt overrides、终态结果。
- Step visit：node、lineageCycle、localRunCycle、visit、route、输入快照、输出、状态。
- Attempt：logicalExecutionKey、attempt、前驱 attempt、技术失败原因、原始最终响应、解析结果、终态时间。
- Orchestration Task/Dispatch：ownership、投递状态、终态、与 attempt 的唯一关系。
- Completion reconciliation：receipt identity/digest、跨 Store 收口进度、最终 outcome、retry 是否已调度。
- Event：创建 child Run、提示覆盖、预算覆盖/扩展、人工操作、恢复处理和终态变化。

### 11.2 事件顺序

单个 attempt 的可观察顺序必须满足：

```text
dispatch-created
→ dispatch-accepted/running
→ response-received
→ task/dispatch-terminal
→ attempt-completed | attempt-failed
→ reconciliation-settled
→ retry-scheduled | route-selected | run-terminal | human-waiting
```

上述顺序是跨 Store 的逻辑顺序，不宣称所有记录由一个 SQLite transaction 同时提交。恢复时允许根据 reconciliation 补写缺失的派生事件，但不得产生第二条业务结果或第二个有效后继。

### 11.3 schema 迁移

- 所有新增列提供向前迁移和旧数据默认值。
- 普通历史 Run 迁移为 `parentRunId=null`、`rootRunId=self`。
- 旧 V1 Run 的 policy snapshot 标记为 `v1-review-rounds`；未覆盖时继续读取模板 `maxReviewRounds`。
- 旧 Run 的 lineageCycle 与 localRunCycle 相同；child Run 启用后再沿 root lineage 递增。
- 迁移必须可重复执行，并在部分失败后安全重跑。
- 不删除旧 prompt、step result 或 event 数据。
- 新版本读取旧数据时采用显式兼容分支，不以空字符串或猜测补齐关键语义。

## 12. UI 与可访问性要求

- 使用 STYLEGUIDE 的布局、颜色、字号、间距和阴影层级，不新增硬编码视觉 token。
- 使用现有 shadcn Button、Tabs、Dialog、Select、Input、Textarea 等 primitives。
- Workflows 继续采用安静、低干扰的中性色；状态颜色只表达状态，不作为唯一信息。
- 必填、错误、首次/再次边界、预算耗尽均需可见文字和可访问标签。
- 键盘快捷键按平台显示和处理：macOS 使用 Command 语义，Linux/Windows 使用 Ctrl；Electron 使用 `CmdOrCtrl`。
- 长列表、历史加载和 SSH 预检不得阻塞整个中间区域；显示明确 loading、empty、error 和 retry 状态。
- Folder workspace 与 Git worktree 使用同一产品能力，不把 Git metadata 作为历史或运行的必需条件。

## 13. 实施拆分

### 阶段 A：建立可靠性基线

1. 冻结可回滚的当前实现基线，保留现有未提交工作，不清理用户改动。
2. 为最近异常 Run 建立可重复的故障夹具。
3. 统一 V1 判定协议。
4. 实现 completion receipt、跨 Store reconciliation 和幂等收口。
5. 实现 V1 logicalExecutionKey、ownership CAS、retry outbox 与恢复路径。
6. 修复文件预览 surface 激活。
7. 修复终端轻量隐藏/恢复。
8. 完成 P0 自动化验收。

### 阶段 B：补齐现有产品闭环

1. 增加 Run lineage 与 migration。
2. 在 Run 详情实现“再来一轮”配置流。

## 14. 建议的模块边界

以下是职责边界，不要求机械照搬文件名：

- Engine completion reconciler：统一成功、解析失败、超时和取消的 attempt 收口。
- Completion reconciliation store：持久化跨 Store 收口进度和幂等 receipt。
- Dispatch ownership store：按 logicalExecutionKey 负责唯一活跃派发、CAS 和恢复查询。
- Run lineage service：创建 child Run、校验权限、解析父级历史。
- Run policy resolver：合并模板预算、Run 覆盖与人工扩展。
- Prompt history resolver：解析稳定 node ID 与相对轮次，生成预检错误。
- Workspace surface activation：统一文件、编辑器、浏览器、终端内容激活。
- Terminal visibility controller：区分 Tab 遮挡与 surface suspend。
- Workflow history query：直接从持久化层按 Project/Workspace 查询，不依赖 activeRun。

新文件必须使用具体领域名称，不使用 `helpers`、`utils`、`common` 等模糊模块名；不得通过禁用 max-lines 解决文件过大。

## 15. 测试矩阵

### 15.1 单元与存储测试

- decision protocol 生成与解析一致。
- 相对历史引用在普通 Run、child Run、多轮和缺失历史时结果正确。
- V1 review round、V2 route traversal 与 attempt 计数互不影响。
- lineage 无环、权限相同、旧 Run 默认值正确。
- completion reconciliation 在每个可失败点重启后幂等续作。
- 唯一活跃 dispatch 约束覆盖并发事务。

### 15.2 主进程集成测试

- Agent 正常完成、非法输出、超时、取消、重复完成和进程重启。
- 原 task/dispatch 和 attempt 均终态、reconciliation settled 后才创建后继 attempt。
- 达到技术重试或业务轮次预算后 Run 必然收敛。
- child Run 继承模板快照和历史，但不修改 parent。
- 历史查询在没有 activeRun 时仍返回当前 Project 数据。

### 15.3 Renderer 交互测试

- 模板、当前运行和历史入口可达。
- `completed` Run 的“再来一轮”生成一个且仅一个 draft child Run。
- 首次/再次提示词的必填、历史引用和预览错误持续可见。
- 文件预览可从 Workflows、History 和 Run 配置态切回 workspace surface。
- preview replacement、固定 Tab、split group 和键盘焦点不回归。

## 16. 可观测性与诊断

日志和诊断导出至少包含以下关联键：

- `runId/rootRunId/parentRunId`；
- `stepId/visit/attemptId/lineageCycle/localRunCycle`；
- `taskId/dispatchId/agentId`；
- `decisionProtocolVersion`；
- `terminalReason/retryReason/routeId`。

日志不得记录凭据、token 或不必要的完整用户敏感内容。提示词和原始响应应保存在受控的 Run 诊断存储中，普通日志只记录长度、哈希和结构化错误。

历史详情需要提供“复制诊断摘要”，用于复现故障，但默认隐藏敏感正文。

## 17. 发布与回滚

- P0 独立发布或先合并，不能与大规模 V2 UI 重构绑定为一个不可拆包变更。
- 数据迁移上线后，旧版本如果不能理解新 child Run，应至少安全忽略，不得破坏数据库。
- V2 使用显式 feature gate；关闭 gate 后仍能查看历史和运行既有 V1 模板。
- 若发现重复派发，优先关闭新 Run 创建与自动重试入口，保留历史查看和诊断导出。
- 每个阶段保留安装包级回滚验证；开发构建成功不等于可发布。

## 18. 完成定义

只有同时满足以下条件，当前工作流整改才可标记完成：

- 最近一次重复判定故障有自动化回归用例，旧 attempt 不再泄漏。
- 所有 Run 在成功、失败、预算耗尽、人工结束和恢复后都能进入明确终态或明确等待态。
- `completed` Run 可创建不可变、有血缘、可审计的 child Run，并修改本次提示词和轮次。
- 当前 Project 的工作流历史有稳定入口，重开 Workflows 后仍可查询。
- 首次与再次提示词边界、历史 preset、保存校验和运行预检全部落地。
- 文件预览和恢复会话样式回归具备本机 Folder、Git worktree 自动化覆盖。
- V2 三个代表性模板均通过通用 Engine、历史、恢复和路由自动化，V1 历史仍可读。
- 本机 Node/Web/CLI 类型检查、Workflow/Renderer 自动化、Electron 交互测试和 App 构建通过。

### 18.1 完成结论（2026-08-03）

- P0：attempt/reconciliation、判定协议、文件预览 surface 和终端轻量恢复代码与自动化完成。
- P1：child Run 血缘、再来一轮、运行级预算、首次/再次提示词、相对历史变量、Project 历史和实际 Prompt 历史完成。
- P2：通用 V2 编辑器、四类步骤、路由预算、人工处理、历史/导出、恢复/并发和三个代表模板完成。
- M5 本机范围：历史、导出、恢复、防重复、Folder/Git workspace 合同完成。
- SSH Workflow：当前明确不支持并在 preflight 安全拒绝；Windows、Linux、跨 Host 与人工验收移出范围。

据此，本 SPEC v1.2 宣告完成。后续使用中发现的交互、模板、远程执行或业务规则调整均作为新需求进入新的 SPEC，不重新打开本合同。

## 19. 最终建议

本合同已按 **P0 可靠性与回归 → P1 产品闭环 → P2 通用工作流 V2 → M5 本机可靠性** 完成交付。

不要先扩展画布或新增专用节点。当前最高风险是 Engine 在失败、重试和恢复时不能保证 task/dispatch/attempt 同步收口；在这个基础不稳时增加“再来一轮”和自由编排，会把重复执行、历史错乱和无法结束的问题成倍放大。

后续优先从用户实际测试中收集新需求，不再把 Windows、Linux、SSH、截图录屏或人工操作结果作为本 SPEC 的遗留项。
