# 通用工作流配置与轮次节点历史变量

## 1. 目标

工作流只描述通用的“向 Agent 发送提示词、保存最终文本、根据结果流转”的过程，不在
引擎中固化 SPEC、代码、评审、Artifact 或 Review Aggregate 等业务概念。

同一个配置模型应能表达：

- 生成 → 评审 → 判定 → 不满足时返回生成；
- 多个普通 Agent 串行或并行协作；
- 首次进入和循环再次进入使用不同提示词；
- 任意步骤通过轮次和稳定节点 ID 引用历史最终文本；
- 达到循环上限或结果无法判定时等待人工处理。

## 2. 核心模型

### 2.1 工作流是步骤图

工作流由四种通用步骤组成：

```ts
type WorkflowStepKind = 'agent' | 'decision' | 'human' | 'end'
```

- `agent`：向一个或多个 Agent 发送提示词，输出 Agent 最终返回文本。
- `decision`：向判定 Agent 发送提示词，把最终返回解析为二元结果。
- `human`：暂停并等待人工选择下一条路径，可附带一段人工文本。
- `end`：结束工作流。

“生成 SPEC”“实现代码”“评审代码”都只是 `agent` 步骤的名称、提示词和角色配置，
不是新的引擎节点类型。

### 2.2 每次执行只追加一条历史

每个步骤每执行一次，Engine 都向 Run 的执行历史追加一条记录，不覆盖前一轮：

```ts
type WorkflowHistoryEntryV1 = {
  sequence: number
  stepId: string
  stepName: string
  stepKind: WorkflowStepKind
  visit: number
  cycle: number
  attempt: number
  promptText: string | null
  finalText: string
  agentOutputs: {
    slotId: string
    agentIdentity: string
    finalText: string
  }[]
  decision: boolean | null
  createdAt: string
}
```

逻辑输出只有 `finalText`。Agent 身份、Session、Dispatch、摘要哈希、投递回执和原始
Transcript 属于 Engine 证据，不进入提示词模板的业务数据模型。

并行步骤仍只产生一条历史记录。Engine 按角色槽位和 Agent 身份稳定排序，将各 Agent 的
最终文本组合为该步骤的 `finalText`；模板也可以读取单个 `agentOutputs`。

## 3. 轮次与节点历史变量

### 3.1 基本语义

每个节点都有工作流内唯一且稳定的 `nodeId`。节点名称可以修改，`nodeId` 不随名称改变。
Engine 在只追加的执行历史之上构建按轮次和节点 ID 查询的索引：

```ts
type WorkflowRoundHistoryV1 = Record<
  number,
  {
    nodes: Record<
      string,
      {
        output: string
      }
    >
  }
>
```

模板统一使用：

```text
{{ history[round].nodes["nodeId"].output }}
```

| 变量                                             | 含义                       |
| ------------------------------------------------ | -------------------------- |
| `history[1].nodes["generate"].output`            | 第 1 轮 generate 节点输出  |
| `history[-1].nodes["review"].output`             | 上一轮 review 节点输出     |
| `history[-2].nodes["judge"].output`              | 上两轮 judge 节点输出      |
| `history[currentRound].nodes["generate"].output` | 当前轮 generate 已完成输出 |

负数轮次相对于当前即将执行的步骤计算。历史引用只读取成功完成并已持久化的节点输出，
不读取当前正在运行、失败、取消或仅已投递的步骤。

### 3.2 系统变量

```text
{{goal}}          Run 的根目标
{{workflow.name}} 工作流名称
{{step.name}}     当前步骤名称
{{visit}}         当前步骤第几次进入，从 1 开始
{{cycle}}         当前循环轮次，从 1 开始
{{attempt}}       当前步骤本次进入的重试次数
```

### 3.3 循环中的语义

历史是只追加序列，循环跳回旧步骤时不清空。

例如：

```text
1  生成
2  评审
3  判定：不完成
4  生成
5  评审
6  判定：完成
```

第二轮执行“生成”时可以明确引用：

- `{{ history[-1].nodes["judge"].output }}`：上一轮判定；
- `{{ history[-1].nodes["review"].output }}`：上一轮评审；
- `{{ history[-1].nodes["generate"].output }}`：上一版生成结果。

因此引用不会因步骤插入、并行执行或节点显示名称改变而漂移。

### 3.4 缺失值

普通模板引用不存在的历史变量时，模板校验失败，不允许启动 Run。

首次进入和再次进入需要不同历史深度时，使用提示词变体，不通过“空字符串替换”掩盖
配置错误。

## 4. 提示词配置

### 4.1 每个 Agent 步骤都有可编辑模板

```ts
type WorkflowPromptVariantV1 = {
  when: 'first-visit' | 'repeat-visit' | 'always'
  template: string
}

type WorkflowPromptV1 = {
  variants: WorkflowPromptVariantV1[]
  completionCriteria: string
}
```

匹配顺序为 `first-visit` 或 `repeat-visit`，最后回退到 `always`。同一进入状态只能命中
一个变体。

`completionCriteria` 通过 `{{criteria}}` 插入模板。模板使用了 Agent 时必须包含
`{{criteria}}`，避免界面配置了判定条件但实际没有发送给 Agent。

示例：

```json
{
  "variants": [
    {
      "when": "first-visit",
      "template": "目标：\n{{goal}}\n\n请生成第一版 SPEC。\n\n完成条件：\n{{criteria}}"
    },
    {
      "when": "repeat-visit",
      "template": "目标：\n{{goal}}\n\n上一轮判定：\n{{ history[-1].nodes[\"judge\"].output }}\n\n上一轮评审：\n{{ history[-1].nodes[\"review\"].output }}\n\n上一版内容：\n{{ history[-1].nodes[\"generate\"].output }}\n\n请修订内容。\n\n完成条件：\n{{criteria}}"
    }
  ],
  "completionCriteria": "覆盖全部需求、边界条件和验收标准，并给出最终完整结论。"
}
```

### 4.2 Agent 输出

Agent 的逻辑输出就是其当前 Provider Session 中与本次 Dispatch 绑定的完整最终回复文本。

Agent 不需要：

- 写工作流专用 JSON；
- 调用 Orca CLI 上报完成；
- 理解 Task、Dispatch、Artifact 或 Run ID；
- 在最终回复中输出引擎内部字段。

Engine 负责确认 Agent 已接收消息、已开始执行并已结束，再从绑定的 Session Transcript
读取完整最终回复。无法证明身份、开始、结束或完整性时进入人工处理，不能使用终端屏幕
摘要猜测结果。

## 5. 统一消息发送

Say Hi、普通人工消息和工作流步骤共用同一个 `AgentMessageDelivery`：

```ts
type AgentMessageDeliveryRequest = {
  target: {
    executionHostId: string
    worktreeId: string
    paneKey: string
    agentLifecycleId: string
    providerSessionId: string | null
  }
  text: string
  requireIdle: boolean
  source: 'say-hi' | 'manual' | 'workflow'
  sourceId: string | null
}
```

该服务统一完成：

- Agent、Pane、Host、Workspace 和 Session 身份校验；
- idle/permission 检查；
- bracketed paste、提交和长文本分块；
- 投递回执、部分发送失败和重复投递保护；
- 本地、Folder Workspace、Git Worktree、SSH 和 Runtime Host 路由。

Say Hi 只是 `text = "hi"` 的普通调用。工作流步骤只是把渲染后的模板文本作为 `text`
调用同一服务，不再维护另一套发送语义。

## 6. 二元判定步骤

### 6.1 判定仍是普通提示词

判定步骤与普通 Agent 步骤使用相同的提示词变体、历史变量、发送服务和最终文本采集。

区别只在于 Engine 对最终文本执行二元解析。

### 6.2 冻结输出约定

判定 Agent 最终文本的第一条非空行必须且只能是：

```text
完成
```

或：

```text
不完成
```

其余文本是判定理由，完整保存在历史的 `finalText` 中。

Engine 只解析第一条非空行：

- `完成` → `decision = true`；
- `不完成` → `decision = false`；
- 其他内容 → 判定无效，按该步骤重试策略处理，耗尽后进入人工等待。

不再使用 `approve`、`revise`、`request-human`、`stop-at-review` 四态结果。

### 6.3 流转

```ts
type WorkflowDecisionRoutesV1 = {
  whenTrue: WorkflowRouteV1
  whenFalse: WorkflowRouteV1
  whenInvalid: WorkflowRouteV1
}

type WorkflowRouteV1 = {
  targetStepId: string
  maxTraversals?: number
  onExhaustedStepId?: string
}
```

- `whenTrue` 通常进入下一阶段或 `end`；
- `whenFalse` 通常回到需要重新执行的 Agent 步骤；
- `whenInvalid` 通常进入 `human`。

任意 Route 都可以配置 `maxTraversals`。达到上限时不再走该 Route，转到
`onExhaustedStepId` 指定的人工步骤。循环上限不属于 Review 节点，也不与 Retry
attempt 混用。

## 7. 人工步骤

人工步骤可以配置通用动作：

```ts
type WorkflowHumanRouteV1 = {
  id: string
  label: string
  targetStepId: string
  requiresText: boolean
  requiresConfirmation: boolean
}
```

人工提交的文本也追加为该轮人工节点的输出。因此人工选择“再走一轮”并填写意见后，
下一步可通过 `{{ history[-1].nodes["human"].output }}` 读取，不需要专用的
`humanFeedback` 占位符。

## 8. 通用定义

```ts
type WorkflowDefinitionV2 = {
  schemaVersion: 2
  name: string
  entryStepId: string
  roleSlots: WorkflowRoleSlotV2[]
  steps: (WorkflowAgentStepV2 | WorkflowDecisionStepV2 | WorkflowHumanStepV2 | WorkflowEndStepV2)[]
}

type WorkflowAgentStepV2 = {
  id: string
  name: string
  kind: 'agent'
  roleSlotIds: string[]
  execution: 'single' | 'parallel' | 'sequential'
  prompt: WorkflowPromptV1
  retryPolicy: WorkflowRetryPolicyV2
  next: WorkflowRouteV1
}

type WorkflowDecisionStepV2 = {
  id: string
  name: string
  kind: 'decision'
  roleSlotIds: [string]
  prompt: WorkflowPromptV1
  parser: 'binary-complete'
  routes: WorkflowDecisionRoutesV1
  retryPolicy: WorkflowRetryPolicyV2
}
```

Agent 步骤没有 `artifactKind`、`outputSchema`、`reviewPolicy` 或领域专用
`inputBindings`。需要传递什么内容完全由提示词模板和轮次节点历史变量决定。

## 9. 表达“生成 → 评审 → 判定”循环

```json
{
  "schemaVersion": 2,
  "name": "生成与评审",
  "entryStepId": "produce",
  "steps": [
    {
      "id": "produce",
      "name": "生成",
      "kind": "agent",
      "roleSlotIds": ["producer"],
      "execution": "single",
      "prompt": {
        "variants": [
          {
            "when": "first-visit",
            "template": "目标：\n{{goal}}\n\n请生成内容。\n\n完成条件：\n{{criteria}}"
          },
          {
            "when": "repeat-visit",
            "template": "目标：\n{{goal}}\n\n上一轮判定：\n{{ history[-1].nodes[\"judge\"].output }}\n\n上一轮评审：\n{{ history[-1].nodes[\"review\"].output }}\n\n上一版内容：\n{{ history[-1].nodes[\"produce\"].output }}\n\n请重新生成。\n\n完成条件：\n{{criteria}}"
          }
        ],
        "completionCriteria": "输出完整、可直接评审的最终内容。"
      },
      "retryPolicy": { "maxAttempts": 2, "onExhausted": "human" },
      "next": { "targetStepId": "review" }
    },
    {
      "id": "review",
      "name": "评审",
      "kind": "agent",
      "roleSlotIds": ["reviewers"],
      "execution": "parallel",
      "prompt": {
        "variants": [
          {
            "when": "always",
            "template": "目标：\n{{goal}}\n\n待评审内容：\n{{ history[currentRound].nodes[\"produce\"].output }}\n\n请给出完整评审结论。\n\n完成条件：\n{{criteria}}"
          }
        ],
        "completionCriteria": "明确列出是否存在未解决问题及其依据。"
      },
      "retryPolicy": { "maxAttempts": 2, "onExhausted": "human" },
      "next": { "targetStepId": "judge" }
    },
    {
      "id": "judge",
      "name": "判定",
      "kind": "decision",
      "roleSlotIds": ["judge"],
      "prompt": {
        "variants": [
          {
            "when": "always",
            "template": "目标：\n{{goal}}\n\n评审结论：\n{{ history[currentRound].nodes[\"review\"].output }}\n\n当前产出：\n{{ history[currentRound].nodes[\"produce\"].output }}\n\n请判断是否满足完成条件。第一条非空行只能输出“完成”或“不完成”，随后说明理由。\n\n完成条件：\n{{criteria}}"
          }
        ],
        "completionCriteria": "当前产出满足目标，且评审中没有未解决的实质问题。"
      },
      "parser": "binary-complete",
      "routes": {
        "whenTrue": { "targetStepId": "end" },
        "whenFalse": {
          "targetStepId": "produce",
          "maxTraversals": 3,
          "onExhaustedStepId": "human"
        },
        "whenInvalid": { "targetStepId": "human" }
      },
      "retryPolicy": { "maxAttempts": 2, "onExhausted": "human" }
    },
    {
      "id": "human",
      "name": "人工处理",
      "kind": "human",
      "routes": [
        {
          "id": "continue",
          "label": "填写意见并再走一轮",
          "targetStepId": "produce",
          "requiresText": true,
          "requiresConfirmation": true
        },
        {
          "id": "end",
          "label": "结束工作流",
          "targetStepId": "end",
          "requiresText": true,
          "requiresConfirmation": true
        }
      ]
    },
    { "id": "end", "name": "完成", "kind": "end" }
  ]
}
```

将“生成”模板替换为 SPEC、代码、文案或测试方案提示词即可复用同一个定义结构。

## 10. UI

模板编辑界面按通用字段展示：

1. 步骤名称与类型；
2. Agent 角色和单个/并行/顺序执行方式；
3. 首次进入提示词；
4. 再次进入提示词；
5. 完成条件；
6. 可通过轮次、节点 ID 和输出字段选择器插入历史变量；
7. 二元判定的完成、不完成和无效结果去向；
8. 循环边次数上限与耗尽后的人工步骤。

界面不要求用户理解 Artifact、Aggregate、Dispatch 或 JSON Schema。

## 11. 验收

- 任意 Agent 步骤只发送渲染后的文本，并保存完整最终回复文本。
- `history[round].nodes[nodeId].output` 在首次执行和循环后均指向正确历史。
- 循环不会覆盖旧历史，Run 重启后相对变量解析结果不变。
- 首次和再次进入可以使用不同模板，缺失历史引用在启动前被发现。
- Say Hi、人工消息和工作流消息使用同一投递服务与安全检查。
- 判定 Agent 只有完成/不完成两个有效结果。
- 不完成按配置跳转，达到通用边预算后进入人工步骤。
- 人工文本作为人工节点的普通历史输出，可由下一步通过轮次和节点 ID 引用。
- 本地、Folder Workspace、Git Worktree、SSH 和 Runtime Host 使用相同配置语义。

## 12. 迁移边界

现有 V1 的 Produce、Review、Artifact、Review Aggregate 和四态 Decision 可继续读取历史 Run，
但不再作为新模板的配置模型。

V2 迁移顺序：

1. 增加只追加执行历史和相对变量渲染器；
2. 统一 Say Hi 与 Workflow 的 AgentMessageDelivery；
3. 从绑定 Transcript 自动采集 Agent 最终文本；
4. 增加 Agent、Decision、Human、End 四种通用步骤；
5. 将三个内置模板迁移为 V2；
6. V1 只读，停止创建新的 V1 模板。
